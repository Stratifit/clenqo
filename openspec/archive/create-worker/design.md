## 1. Approved decision record (normative)

| ID | Decision |
|---|---|
| BD-W1 | Employee↔branch is many-to-many from V1: `employee_branches` is the authoritative operational authorization relationship; no scalar `employees.branch_id` authorization model; supports 1→5→20→100+ branches. |
| BD-W2 | Employee statuses exactly `active / temporarily_unavailable / on_leave / inactive`; no `suspended`. Lifecycle status is distinct from assignment availability; `inactive` blocks new assignments (WORKER §5/§79). |
| BD-W3 | Employment types exactly `full_time / part_time / minijob / flexible`; no `on_call` (WORKER §3; DATABASE §23.1's `on_call` NOT adopted in V1). |
| BD-W4 | Exactly one Job per confirmed Booking in V1; schema extensible to future Booking→multiple Jobs (no permanent 1:1 hard constraint); creation idempotent; retries never duplicate. |
| BD-W5 | Job number `JOB-<year>-<sequence>` (e.g. JOB-2026-000123), org-wide unique, ONE monotonic per-org sequence, year from the source booking's branch-local `scheduled_start`, never reset, never reused, concurrency-safe; UUID stays the internal id. |
| BD-W6 | Immediate post-commit Job creation: booking confirmation transaction commits → Worker creates the Job → idempotency → exactly one Job. Creation failure never rolls back/cancels the confirmed booking; transient confirmed-booking-without-job is permitted and converges on retry. Worker owns creation; Booking owns confirmation. Mechanism = TD-W1. |
| BD-W7a | Explicit cross-domain contracts; neither domain writes the other's tables. Job→Booking derived transitions (`assigned`/`in_progress`/`completed`) go through a Booking-owned transition contract; Booking→Job effects (create/reschedule/cancel/no_show) go through Worker-owned contract functions. Job events authoritative for derived booking transitions; booking events authoritative for booking-driven job effects. Loop prevention structural: derived booking transitions never call back into Worker. |
| BD-W7b | Booking reschedule → same Job identity, interval updated to the new window, existing assignment retained then revalidated against the new interval; invalid → flagged for manager replacement (never silently unassigned); history/events preserved. |
| BD-W7c | Booking cancellation (permitted states only; never once booking `in_progress`) → Job becomes `cancelled`, assignments released (status `cancelled`, rows kept), Job never deleted, cancellation reason linkage preserved, events/audit on both sides. |
| BD-W7d | Booking `no_show` → Job becomes `cancelled` + incident of type `no_show` recorded on the job; NO new job state; Booking remains authoritative for the operational outcome. |
| BD-W8 | Exactly ONE non-terminal (active/pending) assignment per Job at any commit, DB-enforced (partial unique) + transactional validation; `job_assignments` stays structurally multi-row for future team cleaning; no team workflow in V1. |
| BD-W9 | Immediate assignment: authorized manager assigns → assignment created `active`, no acceptance gate; Job becomes `assigned` at that moment (mirrors Booking §34); `accepted`/`declined` remain reserved documented statuses; no acceptance timeout; reassignment manager-controlled (old assignment `cancelled` + history kept → new active, atomic in one transaction); server-authoritative, idempotent, audited. |
| BD-W10 | Change 6 = workforce foundation + internal operations (employees, employee_branches, skills/qualifications, availability/exceptions, user linkage, jobs + snapshots + numbering, assignments, lifecycle/events/audit, minimal no_show incident, Booking↔Job contracts, staff-authoritative transitions, internal UI, RLS). Change 7 = Cleaner Execution PWA (cleaner routes, en_route/check-in/out cleaner flows, checklists, photos/Storage, offline, push, self-service, acceptance UX). Migration 0012. |
| BD-W11 | Skills = Worker-owned, org-wide `skill_key` strings from a documented key namespace; NO registry table, no branch vocabularies, no Service-Catalog→skill derivation (catalog must not participate in assignment); `employee_skills` carries qualification metadata; `level` reserved (no V1 semantics); jobs carry `required_skills` set manually by authorized staff; validation at assignment time ONLY; skills never affect Scheduling capacity; expired mandatory qualification cannot satisfy a new assignment; historical assignments unaffected; `employees.manage` administers employee skills, `jobs.manage`/`jobs.assign` job requirements; no production seed content; no new permission. |
| BD-W12 | `employees.user_id` nullable (records may exist without app access); Auth stays Auth-domain; access provisioned via existing `users.invite`; employment status ≠ application role (`cleaner` is a role, not an employment type); `memberships`+`membership_branches` remain the RLS authorization anchor while `employee_branches` governs operational eligibility; cleaner keeps existing `jobs.view`+`search.use`; deactivation blocks new assignments, preserves history, never deletes the Auth user; no cleaner self-service in Change 6. |
| BD-W13 | Scheduling capacity stays the branch-level concurrency cap (default 3, per-branch configurable) — workforce data is NOT a Scheduling input in V1. Availability/status/skills/branch authorization/assignment conflicts are assignment-eligibility concerns only. Multi-branch employees never contribute capacity to multiple branches; a global per-employee interval-conflict check prevents overlapping assignments across all branches. Confirmed-unassigned jobs occupy capacity through the booking occupancy model. **Bookings are the single authoritative occupancy source; the Change 3 speculative `jobs` probe is removed.** Slot holds, rescheduling, cancellation behavior unchanged. Workforce-derived capacity deferred to a future dedicated decision. |

**S15 boundary (verbatim, binding):** "Scheduling answers whether the requested work can be performed in the requested interval from branch, service, capacity, and conflict constraints — it counts eligible resources but never selects one. Assignment answers which eligible, available worker is chosen to perform it — it may rank and select only among candidates Scheduling has already established as feasible; neither domain performs the other's question."

## 2. Domain boundary

Worker owns employees, skills/qualifications, employee availability, jobs, assignments, the job execution lifecycle, and incidents. It never owns authentication (BD-W12), customer booking lifecycle (Booking), pricing (no price math in Worker; `pricing_version_id` is a reference only), scheduling feasibility (Scheduling), payment, or notification delivery. Assignment selects only among candidates the eligibility validator establishes as feasible; Scheduling is never invoked to choose a worker, and no second availability engine is created (TD-W10).

## 3. Data model (conceptual; implemented by migration 0012)

Conventions (0011 pattern): UUID PKs; `organization_id` NOT NULL everywhere; `branch_id` NOT NULL on branch-scoped tables; composite same-branch FKs where a child references two org/branch parents; `timestamptz` UTC; `created_at/updated_at`; RLS enabled at creation with combined policies via 0006 helpers; no FORCE.

**3.1 `employees`** — org-scoped. `employee_number text` CHECK `^EMP-[0-9]{6}$`, UNIQUE per org, allocated from `employee_number_sequences` (below). `first_name`, `last_name`, `phone?`, `email?`, `preferred_language?`, `employment_type` CHECK (`full_time/part_time/minijob/flexible` — BD-W3), `status` CHECK (`active/temporarily_unavailable/on_leave/inactive` — BD-W2) default `active`, `hire_date date?`, `termination_date date?`, `user_id uuid?` (nullable FK to `auth.users` via profiles convention — BD-W12). Indexes `(organization_id, status)`, `(user_id)`.

**3.2 `employee_number_sequences`** — `organization_id` PK FK→organizations ON DELETE CASCADE, `last_sequence bigint` ≥0, updated_at. Mirrors `booking_number_sequences` (BD-W5 numbering discipline; EMP- is the DATABASE §58 example format, org-unique, monotonic, never reused).

**3.3 `employee_branches`** (BD-W1) — `employee_id` FK, `branch_id` FK; UNIQUE `(employee_id, branch_id)`; org+branch NOT NULL; the authoritative operational eligibility relationship. Index `(branch_id)`.

**3.4 `employee_skills`** (BD-W11) — `employee_id` FK; `skill_key text` CHECK against the documented key namespace (`home_cleaning`, `deep_cleaning`, `commercial_cleaning`, `move_out_cleaning`, `specialized_cleaning`, `window_cleaning` — the keys appearing in WORKER §9/DATABASE §24/SCHEDULING §15 documentation; CHECK-constrained, extensible by migration, NOT a registry table); `qualification_status text?` CHECK (`pending/qualified/expired`), `qualification_date date?`, `expiry_date date?`; `level int?` (reserved, no V1 semantics). UNIQUE `(employee_id, skill_key)`.

**3.5 `employee_availability`** — recurring weekly availability (DATABASE §25.1): `employee_id` FK, `weekday smallint` CHECK 0–6, `start_time time`, `end_time time`, `effective_from date` default today, `effective_until date?`. No employee-wide overlap enforcement in DB (multi-row schedules are legitimate); consistency is the domain layer's concern.

**3.6 `employee_availability_exceptions`** — date/time-scoped overrides (DATABASE §25.2, WORKER §13): `employee_id` FK, `exception_type` CHECK (`unavailable/available`), `start_at timestamptz`, `end_at timestamptz`, `reason?`. An `unavailable` exception overrides recurring availability in its window; `available` widens it. CHECK `end_at > start_at`.

**3.7 `jobs`** — `organization_id`, `branch_id` NOT NULL; `booking_id uuid?` FK→bookings (nullable: internal operational jobs are documented, WORKER §15/§17; V1 creates jobs only from bookings); **partial UNIQUE index `uq_jobs_one_per_booking on (booking_id) where booking_id is not null`** — BD-W4 one-per-booking enforced, future multi-job needs only constraint relaxation; `job_number text` CHECK `^JOB-[0-9]{4}-[0-9]{6}$` UNIQUE per org; `status` CHECK (`pending/assigned/en_route/checked_in/in_progress/completed/cancelled`) default `pending`; `scheduled_start/scheduled_end timestamptz` NOT NULL; `timezone text` (branch tz at creation); **snapshot jsonb `job_snapshot`** (TD-W3, below); `required_skills text[]` default `{}` (BD-W11); `pricing_version_id uuid?` (reference only — no price data); `assignment_flag_reason text?` (BD-W7b manager-replacement flag); `completed_at?`, `cancelled_at?`, `cancellation_reason?`. Indexes `(branch_id, scheduled_start)`, `(booking_id)`, `(status)`.

**3.8 `job_assignments`** — `job_id` FK, `employee_id` FK; `assignment_status` CHECK (`pending/accepted/declined/active/completed/cancelled`) default `active` (BD-W9: V1 writes only `active/completed/cancelled`); `assigned_at timestamptz` default now, `assigned_by uuid?` (auth user), `accepted_at?/declined_at?` (reserved, BD-W9). **Partial UNIQUE `uq_job_assignments_one_active on (job_id) where assignment_status in ('active','pending')`** — BD-W8 invariant. Index `(employee_id, assignment_status)`.

**3.9 `job_events`** — append-only (BEFORE UPDATE OR DELETE guard trigger raises; mirrors 0011 booking_events). `job_id` FK; `event_type` CHECK (`job_created, job_assigned, job_unassigned, job_rescheduled, job_started, check_in, check_out, job_completed, job_cancelled, incident_reported, assignment_flagged`); `metadata jsonb`; `actor_type` CHECK (`staff/system/customer`); `actor_user_id?`. Index `(job_id, created_at)`.

**3.10 `incidents`** — minimal model (DATABASE §29 + BD-W7d): `organization_id`, `branch_id`, `job_id` FK; `reported_by uuid?`; `incident_type` CHECK incl. `no_show` (plus documented types `property_damage, access_problem, customer_issue, cleaner_issue, safety_issue, late_arrival`); `severity?` CHECK (`low/medium/high/critical`); `description?`; `status` CHECK (`open/resolved`) default `open`; `created_at`, `resolved_at?`. No quality workflow.

**3.11 `job_number_sequences`** — `organization_id` PK FK→organizations ON DELETE CASCADE, `last_sequence bigint` ≥0. Row-locked allocation inside the job-creation transaction; year component from the booking's branch-local `scheduled_start`; monotonic counter never resets (BD-W5 duplicate-free year boundaries, identical rationale to BD-5).

**3.12 Explicitly absent:** no checklist tables, no photos/Storage, no messaging, no payment/payroll, no team-cleaning workflow tables, no cleaner PWA tables, no automatic-assignment config.

**TD-W3 snapshot strategy (normative):** `jobs.job_snapshot` jsonb is immutable operational data captured at creation from the confirmed booking: `service_label`, `variant_label?`, `addon_labels[]`, `service_address` (the booking's immutable address snapshot, referenced NOT duplicated as live data — copied once into the job snapshot for PWA stability), `customer_display` (minimized per WORKER §29–30: first name only), `property_details`, `instructions` (booking internal_notes restricted view per §30), `booking_number`, `scheduled window copy`. The booking's pricing snapshot is NEVER copied — `pricing_version_id` reference only (Pricing ownership preserved).

## 4. Technical decisions (TD-W1…TD-W10 — all resolved here)

**TD-W1 Job-creation mechanism** — Worker-owned function `ensureJobForBooking(bookingId)` invoked in the booking confirmation server action **immediately after the confirmation transaction COMMITs** (BD-W6). Idempotency: the partial unique `uq_jobs_one_per_booking` is the database guarantee; the function first checks for an existing job (fast path) and catches unique violations on concurrent insert as success (convergence). Failure (e.g., transient DB error) throws to the action layer, which logs and returns the confirmed booking with `jobCreation: 'pending'` — the booking is NEVER rolled back; a staff retry action (and the natural next visit of the booking) re-invokes `ensureJobForBooking`. Convergence: exactly one job eventually, provable by the unique index. Why not in-transaction: BD-W6 explicitly forbids coupling booking confirmation atomicity to job creation. Alternatives: background worker (explicitly excluded by BD-W6), trigger-based creation (hidden cross-domain write — violates BD-W7a). Schema: 3.7.

**TD-W2 RLS policy set** — per table, combined select policies using 0006 helpers, cleaner-scoped where applicable:
- `employees`, `employee_number_sequences`: org-wide for `hq_admin/hq_staff`; branch managers via `has_branch_access` (managers see their branches' employees); **cleaner-role: only their own employee row** (`user_id = auth.uid()`).
- `employee_branches`, `employee_skills`, `employee_availability`, `employee_availability_exceptions`: same as employees (staff manage; cleaner reads own via employee join — implemented as `exists` subselect on own employee row).
- `jobs`, `job_events`, `incidents`: org-wide `hq_admin/hq_staff`; branch via `has_branch_access`; **cleaner: jobs where an active assignment of theirs exists** (exists-subselect on `job_assignments`).
- `job_assignments`: staff per above; **cleaner: own assignments only** (`employee_id in (select id from employees where user_id = auth.uid())`).
- `job_number_sequences`, `employee_number_sequences`: `hq_admin/hq_staff/branch_manager` org-wide (mirrors booking_number_sequences).
- All mutations flow through the privileged domain layer (service role); application-role writes are not granted on worker tables (0007 pattern: no `for all` policies; select-only app policies). No FORCE.

**TD-W4 Booking-owned transition contract** — `features/booking` exports `applyJobDerivedBookingTransition(bookingId, kind: 'assigned'|'in_progress'|'completed', ctx)`: validates the booking's current state against the approved transition matrix, updates `bookings.status` if valid, writes the corresponding booking event (`booking_assigned/booking_started/booking_completed`), audit, and is **idempotent** (transitioning to the state it already has is a success no-op). Called by Worker **after** the Worker transaction commits (job event authoritative; booking reflects). Structural loop prevention: this contract never calls back into Worker; booking-side mutations that affect jobs (cancel/reschedule/no_show) originate only from Booking's own staff/customer actions, which call the Worker-owned contract. Alternatives: DB triggers across domains (hidden coupling — rejected); direct table writes (violates BD-W7a).

**TD-W5 Job-number allocation** — inside the job-creation transaction: `SELECT last_sequence FROM job_number_sequences WHERE organization_id = $1 FOR UPDATE` → increment → update → format `JOB-<year>-<seq zero-padded 6>` with year from the booking's **branch-local `scheduled_start`** (branch timezone via the branch row; identical derivation to BD-5/0011). Monotonic → no year-boundary duplicates.

**TD-W6 Availability storage** — two-table model (3.5/3.6) exactly per DATABASE §25.1/§25.2: recurring weekly windows with effective dating, typed exceptions that override. Evaluation (assignment eligibility only) resolves for an instant: exception → recurring → none. DST: instants are UTC; local windows interpreted in the **branch** timezone via the existing scheduling timezone helpers (WORKER §14 branch-tz default).

**TD-W7 Assignment concurrency** — one transaction per assign/reassign: `SELECT … FOR UPDATE` the job row (serializes concurrent assignment attempts) → validate job state (`pending`/`assigned` for assign; reassignment = cancel active assignment + insert new in the SAME transaction) → run the eligibility validator (§7) → insert assignment `active` (partial unique is the final backstop; a race that slips past the lock wait fails on the index and rolls back) → job `pending→assigned` → `job_assigned` event → audit → outbox row → commit → then the Booking transition contract (TD-W4) post-commit. Idempotent retries: re-assign with the same employee and an active assignment already present = success no-op.

**TD-W8 Event/audit payloads** — `job_assigned`: `{employee_id, assigned_by, previous_assignment_id?}`; `job_unassigned`: `{employee_id, reason}`; `job_rescheduled` (worker side): `{previous_scheduled_start/end, new_scheduled_start/end, booking_event_ref}`; `job_cancelled`: `{reason, booking_cancellation_reason?}`; `job_completed`: `{completed_by}`; `incident_reported`: `{incident_id, incident_type}`; `assignment_flagged`: `{employee_id, reason}` (BD-W7b). Audit rows: employee created/updated/deactivated, branch membership changes, skill changes, availability changes, assignment mutations, manager overrides (WORKER §67; AUDIT §100–102). Sensitive-data minimization per §50.

**TD-W9 Migration/seed strategy** — `0012_worker.sql` chained 0001→0012; **no seed content**: no employees, no skills, no schedules, no availability data (BD-W11 production-value discipline; fixtures live only in tests). No provisioning-seed integration is required (unlike cancellation policies, workforce data has no per-branch defaults).

**TD-W10 Scheduling consumption & occupancy unification** — remove the Change 3 speculative `jobs` probe from `loadOccupied` in `features/scheduling/availability.ts`; bookings (status-filtered, Change 5) remain the **single** occupancy source (BD-W13) — jobs never double-count because their booking already occupies. The assignment eligibility validator consumes scheduling *helpers* (interval overlap arithmetic) but never the slot engine; no workforce data enters `getAvailability`.

## 5. Job lifecycle

States (BD-W, WORKER §19–20): `pending → assigned → en_route → checked_in → in_progress → completed`; `pending/assigned → cancelled`. Change 6 staff-authoritative surface: `pending→assigned` (assignment, TD-W7), `assigned→completed` (authorized staff operational completion — the §65 server-authority override path; completion then drives Booking `completed` via TD-W4), `pending/assigned→cancelled` (booking-driven BD-W7c; staff cancellation is not an independent V1 surface — booking cancellation is the only source, per BD-W7c's booking-authoritative design). `en_route/checked_in/in_progress` exist in the model with their triggers reserved for Change 7 cleaner actions (staff override capability exists per WORKER §33/§65 but no Change 6 UI exercises it). Terminal: `completed/cancelled`. No new states (BD-W7d: no_show is a booking outcome + incident, never a job state).

## 6. Booking↔Job contracts (both directions, loop-proof)

**Booking → Worker (Worker-owned contract functions):**
- `ensureJobForBooking(bookingId)` — on confirmation (post-commit, TD-W1); retryable/convergent.
- `propagateRescheduleToJob(bookingId, previousWindow, newWindow)` — same job, interval updated, assignment retained + revalidated (availability/conflict check against the new interval), invalid → `assignment_flagged` event + `assignment_flag_reason` set (never silent unassign) + `job_rescheduled` event (BD-W7b).
- `propagateCancellationToJob(bookingId, reason)` — job `→cancelled` (only from `pending/assigned`; a job already past those states with a cancelled booking is a data error), assignments →`cancelled`, events (BD-W7c).
- `propagateNoShowToJob(bookingId, reason)` — job `→cancelled` + `no_show` incident + events (BD-W7d).
Trigger points: the corresponding Booking server actions call these after their own transaction commits (booking events authoritative for booking-driven effects).

**Worker → Booking (Booking-owned contract, TD-W4):** `applyJobDerivedBookingTransition` on `assigned` (assignment), `in_progress` (future check-in/start), `completed` (completion). Idempotent, state-guarded, fail-closed-audited, called post-Worker-commit.

**Loop prevention (structural):** derived booking transitions never invoke Worker; booking-action effects on jobs never write booking state. The dependency graph is a DAG: Booking-actions → Worker-contracts → job state; job actions → Booking-contract → booking state.

## 7. Assignment eligibility validator (order normative)

For candidate employee E and job J: (1) E exists; (2) `status='active'` (BD-W2; others ineligible); (3) branch authorized via `employee_branches` (BD-W1); (4) every `required_skills` key present on E (BD-W11); (5) mandatory qualifications valid at J's `scheduled_start` (expired → reject; BD-W11); (6) recurring availability covers J's interval (branch-tz, TD-W6); (7) no `unavailable` exception overlaps J's interval (overrides availability); (8) **global cross-branch interval conflict**: no non-terminal assignment of E on any job in any branch overlaps J's window (BD-W13 multi-branch safety); (9) J's timing valid (start<end); (10) J has no other non-terminal assignment (BD-W8 backstop). Failure returns a stable, specific error code per failed rule. Scheduling feasibility is NOT re-derived here (S15; the slot was validated when the booking confirmed).

## 8. Internal operations (staff UI/actions)

Permissions (existing catalog only): employees list/detail/create/edit/deactivate, branch memberships, skills, availability = `employees.view`/`employees.manage` (org-scoped for HQ; branch managers scoped via membership_branches); jobs list/detail/search + skill requirements = `jobs.view`/`jobs.manage`; assign/reassign/cancel-assignment = `jobs.assign`. Job search per WORKER §68 (job number, booking number, customer, cleaner, date, status, branch). No cleaner routes/surfaces (PROJECT_STRUCTURE §13 stays empty in Change 6).

## 9. Security summary

RLS per TD-W2 on all ten tables (combined policies, cleaner own-scope subselects, no FORCE); cleaner authority never exceeds own employee row/assignments/jobs; customer data minimized in snapshots (§29–30); deactivation blocks new assignments at validator level + RLS keeps history readable; audit fail-closed transactional (AUDIT §50) for all administrative mutations; no auth changes (BD-W12); employee PII protected by least privilege (WORKER §75).

## 10. Observability

Metrics per WORKER §83: jobs_created, jobs_assigned, assignment_failures, completed_jobs, cancelled_jobs, no_shows, incidents; structured logs carry booking_id/job_id correlation (OBSERVABILITY §9); audit events separate from domain events per established convention.

## 11. Testing strategy

**Unit:** eligibility validator matrix (each rule + cross-branch overlap + expired qualification + status filtering); availability resolution (recurring/exception/override/DST); numbering format/monotonicity/year derivation; transition matrix.
**Domain (pglite, chain 0001→0012):** employee CRUD + M2M branches + status/type CHECKs; EMP-number allocation/concurrency; skills + expiry; availability + exceptions; job creation idempotency (double invoke, concurrent insert race → one job), failure-survival (booking confirmed, job pending, retry converges); JOB-number org uniqueness + year from booking local start; assignment: one-active invariant (two actives rejected), atomic reassignment (history preserved), eligibility failures, cross-branch conflict rejection, deactivation blocks; booking-driven propagation: reschedule (interval update + retain/revalidate + flag), cancel (job cancelled + assignments released + history), no_show (cancelled + incident); derived booking transitions (assigned/completed mirrors, idempotent); audit fail-closed (audit insert failure rolls back); events append-only; outbox rows; RLS denials on all tables incl. cleaner own-row/own-job scope and cross-org/cross-branch denial; occupancy: booking occupies, no job double-count (probe removed).
**Hosted:** `tests/hosted/worker-hosted-verification.test.ts` per the established convention (schema/constraints/RLS/flows/leftovers=0) + full hosted regression Changes 1–6.
